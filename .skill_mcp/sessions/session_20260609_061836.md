## 1. Svelte 5 响应式系统

**相关链接：**
- [Svelte Docs - Overview](https://svelte.dev/docs/svelte/overview)
- [Svelte Docs - $state](https://svelte.dev/docs/svelte/$state)
- [Svelte Docs - $derived](https://svelte.dev/docs/svelte/$derived)
- [Svelte 5 Runes 官方指南](https://svelte.dev/docs/svelte/runes)

### $state vs $derived 对比

| 特性 | `$state` | `$derived` |
|------|----------|------------|
| **本质** | 响应式状态（可读写） | 派生状态（只读，自动计算） |
| **用途** | 存储应用中的可变数据 | 根据其他响应式状态推导新值 |
| **触发更新** | 直接赋值时触发 | 依赖的 `$state` 变化时自动重新计算 |
| **类比** | Vue `ref()` / React `useState()` | Vue `computed()` / React `useMemo()` |

### $state 详解

- **声明式**：`let count = $state(0);` — 定义响应式变量
- **代理模式**：对象和数组内部属性会被 `Proxy` 自动追踪
- **两种形式**：`$state()`（函数式，适合条件初始化）和 `let x = $state(...)`（声明式，更简洁）
- **特殊形式 `$state.raw()`**：跳过 `Proxy` 代理，用于大数组等不需要细粒度追踪的场景

### $derived 详解

- **声明方式**：`let doubled = $derived(count * 2);`
- **惰性计算**：仅在被读取时才计算，未访问不会重复计算
- **自动依赖追踪**：读入的响应式值会自动注册为依赖

### 总结

Svelte 5 通过 Runes 将响应式能力**显式化**：`$state` 管"数据本身"，`$derived` 管"数据的派生关系"。相比 Svelte 4 的隐式响应式（编译器自动分析赋值），Runes 使响应式边界更加清晰，支持自定义 hooks、条件响应式变量等新编程模式。

## 2. Rust async 运行时对比：tokio vs async-std

**相关链接：**
- [Tokio 官网](https://tokio.rs)
- [Tokio GitHub](https://github.com/tokio-rs/tokio)
- [async-std 官网](https://async.rs)
- [async-std GitHub](https://github.com/async-rs/async-std)

### 特性对比表

| 维度 | **tokio** | **async-std** |
|------|-----------|---------------|
| **定位** | 全功能异步运行时（工业级） | stdlib 风格的 async 库 |
| **生态成熟度** | ⭐⭐⭐⭐⭐（绝对主流） | ⭐⭐⭐（活跃但较小） |
| **调度模型** | 多线程工作窃取调度器 | 单线程 / 多线程可选 |
| **网络 I/O** | `tokio::net`（TCP/UDP/Unix） | 基于 `mio`，API 更贴近 std |
| **线程池** | 内置多线程 runtime（可配置 worker） | 默认单线程，需显式启用 |
| **社区采用** | AWS、Cloudflare、Discord 等大量生产系统 | 较小规模项目 |
| **版本** | v1.x 稳定，v2 开发中 | v1.x 稳定，更新频率较低 |

### tokio 核心优势

1. **线程池调度**：N:M 协作式多线程调度，自动平衡负载
2. **丰富生态**：`hyper`（HTTP）、`tonic`（gRPC）、`tower` 中间件等全部以 tokio 为默认后端
3. **精细控制**：可配置 runtime builder（worker 线程数、阻塞任务限制等）
4. **生产验证**：几乎所有大型 Rust async 项目采用

### async-std 设计理念

1. **stdlib 亲和性**：API 设计尽量模仿 `std`，迁移成本极低
   ```rust
   let content = async_std::fs::read_to_string("file.txt").await; // 像 std 一样简单
   ```
2. **轻量**：无线程池调度器，默认单线程运行
3. **兼容性好**：可与 `std` 模块无缝混用

### 选型建议

| 场景 | 推荐 |
|------|------|
| Web 服务（高并发） | **tokio** |
| CLI / 工具类应用 | 均可（async-std 更简洁） |
| 学习 Rust async | **tokio**（生态完整、资料多） |
| 最小依赖嵌入 | **async-std** |

### 总结

**tokio 是事实标准**。提供了完整的异步运行时（调度器、I/O、定时器等），生态最丰富，适合绝大多数生产场景。**async-std** 的价值在于 API 贴近 `std`，适合小型工具或已有 stdlib 习惯的开发者。两者底层都基于 `mio`（操作系统异步 I/O），本质区别在于调度策略和生态成熟度。

## 3. Tailwind CSS v4 关键变化

**相关链接：**
- [Tailwind CSS v4 发布博客](https://tailwindcss.com/blog/tailwindcss-v4)
- [Tailwind CSS v4 迁移指南](https://tailwindcss.com/docs/upgrade-guide)
- [Tailwind CSS v4 文档](https://tailwindcss.com/docs)

### 关键变化一览

#### 🎨 CSS-first 配置（最大范式转变）

| v3 | v4 |
|----|-----|
| 配置在 `tailwind.config.js` | 配置直接在 CSS 文件中完成 |
| JS 中写 `content: ['./src/**/*.{svelte,js}']` | CSS 中写 `@import "tailwindcss";` |
| `plugins: [require('@tailwindcss/forms')]` | CSS 中写 `@plugin "@tailwindcss/forms";` |
| `theme.extend.fontFamily = {...}` | CSS 中写 `@theme { --font-display: "Inter"; }` |

```css
/* v4: 一切在 CSS */
@import "tailwindcss";

@theme {
  --font-display: "Inter", sans-serif;
  --color-brand-50: #fef2f2;
}

@plugin "@tailwindcss/forms";
```

#### ⚡ 性能大幅提升

- **构建速度**：比 v3 快 **3-10x**（不再需要扫描文件内容的正则匹配）
- **内存占用**：显著降低
- **JIT 成为唯一模式**：v4 只有一种构建方式

#### 📦 零默认值 / 按需生成

- v4 **移除了所有预定义的 utility classes**（不再有默认的 `p-4`, `text-center` 等）
- 通过 `@theme` 注册的变量才生成对应的 classes

#### 🆕 新增功能

- **Container Queries 内置**：不再需要额外插件
- **`@variant`**：自定义任意 CSS pseudo-class / at-rule 变体
- **`@slot`**：为组件预留自定义内容插槽
- **CSS Nesting 内置**：可直接在 CSS 中使用嵌套语法

#### 🔄 迁移注意事项

1. **安装新 CLI**：`npm create tailwindcss@latest`
2. **旧配置自动转换**：CLI 会将 `tailwind.config.js` 转换为 CSS-first 格式
3. **自定义类名**：`@utility` 指令替代 v3 的 `theme()` 函数
4. **预检检查**：CLI 会提示破坏性变更

### 总结

Tailwind v4 是一次 **架构级重构**：从 JS 配置驱动转向 CSS-first，移除预定义 classes 改为按需生成。最大收益是**构建速度和性能提升**（3-10x），代价是需要适应新的配置范式。新项目强烈推荐 v4；已有 v3 项目可通过 CLI 工具自动转换配置，但需注意自定义 utility 和插件语法的变化。
